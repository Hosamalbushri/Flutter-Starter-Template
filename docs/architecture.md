# Package Architecture, Module Contracts & Enforcement

This document defines the package categories, dependency directions, public API rules, `FeatureModule` contracts, dependency injection boundaries, navigation boundaries, localization/UI boundaries, and CLI lifecycle workflows enforced across the `flutter-starter-template` Dart Pub Workspace.

---

## 1. Package Categories

Every package in the workspace belongs to one of seven explicit architectural categories (enforced in `test/architecture/package_layering_test.dart`):

| # | Category | Packages | Responsibility |
|---|---|---|---|
| 1 | **Application Shell** (`applicationShell`) | Root package (`flutter_starter_template` / generated `<app_name>`) | Bootstrap (`main.dart`, `app.dart`), global DI composition (`lib/app/di/injection.dart`), root `GoRouter` (`lib/app/router.dart`), `AppShell`, and `enabledFeatures` (`lib/app/features.dart`). |
| 2 | **Feature Packages** (`feature`) | `feature_auth`, `feature_bookmarks`, `feature_collections`, `feature_home`, `feature_notifications`, `feature_profile`, `feature_splash`, plus any feature added via `fst add-feature` | Self-contained vertical feature slices under `packages/features/<name>/` (`presentation/`, optional `domain/` and `data/`). |
| 3 | **Shared Domain Contracts** (`sharedDomainContracts`) | `architecture`, `shared_contracts` | Pure-Dart architectural primitives (`Result`, `Failure`, `UseCase`) and narrow cross-feature domain interfaces (`Session`, `AuthUser`, `BookmarkStatsReader`, `CollectionsReader`, `ActivityNotifier`). |
| 4 | **UI & Design-System Packages** (`uiDesignSystem`) | `app_ui`, `localization`, `theme`, `shared_ui` | Design tokens (`AppSpacing`, `AppRadius`, `AppElevation`, `AppIconSize`, `AppDurations`, `AppBreakpoints`), reusable widgets (`AppScaffold`, `AppLoading`, `AppErrorView`, `AppEmptyState`, etc.), ARB localization (`AppLocalizations`), `ThemeBloc`/`AppColors`, and cross-feature presentation scopes (`SessionScope`). |
| 5 | **Infrastructure & Service Packages** (`infrastructureService`) | `analytics`, `config`, `database`, `database_drift`, `network`, `rev_sync`, `storage` | Reusable technical capabilities: Firebase Analytics, Remote Config/environment config, ObjectBox/Drift persistence, Dio/Retrofit HTTP client, offline-first sync engine (`rev_sync`), and `SharedPreferences`/`FlutterSecureStorage` token storage. |
| 6 | **Platform Integration Packages** (`platformIntegration`) | `app_platform`, `sync_connectivity_plus` | OS/device plugin adapters (permissions, media capture, local notifications, share sheet, network connectivity stream for `rev_sync`). |
| 7 | **Development & Testing Utilities** (`devTestUtilities`) | `test_utils` | Shared fakes (`FakeSession`, fake readers), fixtures (`testUser`, `testFailure`), and `mocktail` helpers. Restricted strictly to `dev_dependencies:`. |

## 2. Dependency Direction & Layer Ranks

Runtime dependencies (`dependencies:` in `pubspec.yaml`) must form a strict Directed Acyclic Graph (DAG) flowing downward across both **category rules** and **numeric layer ranks** (`0` through `5`):

- **Layer 0 (Pure-Dart Foundation)**: `architecture`, `rev_sync` — zero workspace dependencies.
- **Layer 1 (Primitives & Base Contracts)**: `config`, `storage`, `analytics` ($\to$ `architecture`), `app_ui`, `localization`, `shared_contracts` ($\to$ `architecture`), `database` / `database_drift` ($\to$ `rev_sync`), `sync_connectivity_plus` ($\to$ `rev_sync`).
- **Layer 2 (Composed Infrastructure, Platform & Shared Presentation)**: `shared_ui` ($\to$ `shared_contracts`), `network` ($\to$ `config`), `app_platform` ($\to$ `analytics`, `architecture`), `theme` ($\to$ `analytics`, `architecture`).
- **Layer 3 (Dev/Test Harness)**: `test_utils` ($\to$ `analytics`, `app_platform`, `storage`) — never allowed in runtime `dependencies:`.
- **Layer 4 (Base Feature Packages)**: `feature_auth`, `feature_collections`, `feature_home`, `feature_notifications`, `feature_splash`, and features generated by `fst add-feature`.
- **Layer 5 (Capability-Consuming Feature Packages)**: `feature_bookmarks` ($\to$ `feature_collections`), `feature_profile` ($\to$ `feature_auth`).

### Permitted Category Directions

- **Application Shell** $\to$ `feature`, `sharedDomainContracts`, `uiDesignSystem`, `infrastructureService`, `platformIntegration`.
- **Feature Packages** $\to$ `sharedDomainContracts`, `uiDesignSystem`, `infrastructureService`, `platformIntegration`, and (only when allowlisted in `test/architecture/feature_boundaries_test.dart`) a lower-rank `feature`.
- **UI & Design-System Packages** $\to$ `uiDesignSystem`, `sharedDomainContracts`, `infrastructureService`.
- **Platform Integration Packages** $\to$ `platformIntegration`, `infrastructureService`, `sharedDomainContracts`.
- **Infrastructure & Service Packages** $\to$ `infrastructureService`, `sharedDomainContracts`.
- **Shared Domain Contracts** $\to$ `sharedDomainContracts` only.
- **No package** may depend on the **Application Shell** or on **`test_utils`** in runtime `dependencies:`.

## 3. Public API Rules

Enforced by `test/architecture/public_api_contracts_test.dart` and `test/architecture/feature_boundaries_test.dart`:

1. **Single Public Entry Point**: Every workspace package `pkg` exposes exactly one top-level file under `lib/`: `lib/<pkg>.dart`.
2. **Private Implementation Directory**: All other `.dart` files in a package must reside under `lib/src/` (or `lib/l10n/` for generated localization files in `package:localization`).
3. **No Cross-Package `lib/src/` Imports**: Importing or exporting `package:<other>/src/...` from outside `<other>` (including from `test/` or `integration_test/`) is forbidden. Relative imports that escape a package's `lib/` root are also forbidden.
4. **No Internal DI or Locator Leakage**: Package barrels must never export `src/di.dart` or `src/locator.dart`.
5. **Feature Barrel Whitelist**: Feature barrels (`lib/feature_<name>.dart`) may only export:
   - `src/di.module.dart` (`show Feature<Name>PackageModule`)
   - `src/presentation/**` (routes, screens, and intentional capability widgets/BLoCs)
   - `src/domain/entities/**`
   - `src/domain/services/**` (sync lifecycle controller interfaces)
   Feature barrels must never export `src/data/**`, `src/domain/repositories/**`, or `src/domain/usecases/**`.
6. **No Raw Third-Party SDK Re-exports**: Infrastructure barrels must not re-export raw `package:firebase_*/`, `package:shared_preferences/`, or `package:flutter_secure_storage/`.

## 4. `FeatureModule` Contract

Defined in `lib/app/feature_module.dart` and enforced by `validateFeatureModules` at startup (`lib/app/app.dart`) and in `test/architecture/feature_module_contracts_test.dart`:

- **`String get id`**: Required, unique `snake_case` identifier matching `packages/features/<id>` and `feature_<id>`.
- **`Set<String> get requiredFeatures`**: Optional set of sibling feature IDs that must be enabled whenever this feature is enabled (e.g. `_BookmarksModule` declares `{'collections'}`). Validated for existence, non-self reference, and absence of cycles.
- **`FeatureNavigationRegistration? get navigation`**: Optional metadata describing the feature's primary entry route (`routePath`, optional `routeName`, `isShellBranch`).
- **`Future<void> initialize()`**: Optional async hook invoked deterministically during app startup after DI initialization.
- **`FeatureSyncController? get syncController`**: Optional session-scoped background sync lifecycle (`start()` on sign-in, `stop()` on sign-out).
- **`Iterable<RouteBase> get routes`**: Non-shell `GoRoute` trees contributed to the host `GoRouter`. Top-level routes must use unique, absolute paths starting with `/`, and all `GoRoute.name` values across modules must be unique.

## 5. Dependency Injection Boundaries

Enforced by `test/architecture/di_boundaries_test.dart` and `test/architecture/firebase_optional_di_test.dart`:

1. **Micro-Package Pattern**: Each package declares `@InjectableInit.microPackage()` in `lib/src/di.dart` and exports only its generated `<Name>PackageModule` from its barrel.
2. **No Cross-Feature DI Configuration**: A feature package may never reference or register another feature's `Feature*PackageModule`.
3. **Constructor Injection in `domain/` & `data/`**: Feature `domain/` and `data/` layers must never import `package:get_it/get_it.dart` or `locator.dart` (`getIt` access is restricted to `presentation/` widget wiring and the application shell).
4. **No Manual `getIt.register*` in Packages**: Workspace packages under `packages/*/lib/` must not call `getIt.register*` outside generated `*.module.dart` files.
5. **Deterministic Composition Order**: In `lib/app/di/injection.dart`, infrastructure, platform, and `SharedContractsPackageModule` are registered in `externalPackageModulesBefore` strictly before any `Feature*PackageModule`, and `StoragePackageModule` precedes `NetworkPackageModule`.
6. **Safe Optional Fallbacks**: `registerReaderFallbacks(getIt)` in `lib/app/di/reader_fallbacks.dart` registers `NoOpBookmarkStatsReader` and `NoOpCollectionsReader` whenever `feature_bookmarks` or `feature_collections` are excluded, keeping `feature_home` functional without optional features.

---

## 6. Navigation Boundaries

- Features define their own canonical route paths and `GoRoute` trees inside `lib/src/presentation/<name>_routes.dart` and navigate via `go_router` (`context.push`, `context.pushNamed`, `context.go`) without importing the root app's `lib/app/router.dart`.
- The root shell (`lib/app/router.dart`) composes core shell branches (`StatefulShellRoute.indexedStack`) and mounts all enabled feature routes via `...enabledFeatures.expand((f) => f.routes)`.

---

## 7. Localization & UI Rules

Enforced by `test/architecture/localization_and_ui_boundaries_test.dart`:

1. **Domain Layer Purity**: `architecture`, `rev_sync`, `shared_contracts`, and all `packages/features/*/lib/src/domain/` files must never import Flutter widget/UI libraries (`flutter/material.dart`, `flutter/widgets.dart`, `flutter/cupertino.dart`), `app_ui`, `shared_ui`, `localization`, `theme`, `go_router`, or `flutter_bloc`.
2. **Localized User-Facing Copy**: Feature presentation layers must depend on `package:localization/localization.dart` and read user-facing strings via `context.l10n`.
3. **Catalog Parity & Directionality**: `app_en.arb`, `app_vi.arb`, and `app_ar.arb` must maintain 100% key parity, supporting both LTR (`en`, `vi`) and RTL (`ar`) layouts. Shared directional widgets (such as `AppScaffold`'s back button) adapt automatically to `Directionality.of(context)`.
4. **Design Token Single Source of Truth**: Feature packages must consume spacing, radius, elevation, icon size, duration, and breakpoint tokens from `package:app_ui/app_ui.dart` and theme extensions from `package:theme/theme.dart` rather than declaring duplicate token classes or `ThemeExtension`s.
5. **Business-Free Design System**: `packages/app_ui` must remain free of application-specific business copy (bookmarks, collections, etc.).

## 8. Developer Workflows

### How to Add a Workspace Package

1. Create `packages/<name>/pubspec.yaml` with `resolution: workspace` and `packages/<name>/lib/<name>.dart` exporting only public contracts from `lib/src/`.
2. Add `- packages/<name>` under `workspace:` in the root `pubspec.yaml`.
3. Assign `<name>` a category in `_nonFeatureCategories` and a layer rank in `_layers` inside `test/architecture/package_layering_test.dart`.
4. If the package uses Injectable, add `@InjectableInit.microPackage()` in `lib/src/di.dart`, export `<Name>PackageModule` from `lib/<name>.dart`, and register `ExternalModule(<Name>PackageModule)` in `lib/app/di/injection.dart` before feature modules.

### How to Add a Feature

Use the CLI from the project root:

```bash
fst add-feature <feature_name> --source presentation|local|api|sync [--route-path /custom-path]
```

This scaffolds `packages/features/<feature_name>/` (compliant with `app_ui`, `localization`, public barrel rules, and `.fst-feature.json`), registers the feature in `pubspec.yaml`, `lib/app/di/injection.dart`, `lib/app/features.dart` (with `FeatureModule.id`), and `test/architecture/package_layering_test.dart`, and runs codegen, analysis, and tests.

### How to Validate Compliance

Run both the CLI validator and the automated architecture test suite:

```bash
fst validate-features
fvm flutter analyze
fvm flutter test test/architecture
```

### How to Remove a Feature Safely

Use the CLI from the project root:

```bash
fst remove-feature <feature_name> [--dry-run] [--yes] [--force-modified]
```

`fst remove-feature` verifies CLI ownership (`.fst-feature.json`), blocks removal if another feature depends on the target feature or if user-modified files exist without `--force-modified`, removes all wiring entries, validates the remaining feature graph, and runs `pub get`, codegen, `flutter analyze`, and `flutter test` with automatic byte-for-byte rollback on any failure.
